# 架构决策记录（ADR）

本文件记录「象棋教练」框架的关键技术决策与理由。产品层面的完整论证见仓库外的《象棋教练产品设计方案 v0.2》。

## ADR-001：引擎与 UI 解耦为两个进程/线程边界

**决策**：引擎不嵌入 UI，通过 UCI 协议 + 桥接层通信。

**理由**：
- 崩溃隔离——引擎崩了棋盘和数据不丢
- 可替换——Pikafish / 其他引擎插上即用
- 这是皮卡鱼生态（引擎 + 任意 GUI）与整个棋软生态的通用做法，不是自创

**落地**：`src/engine/types.ts`（协议）、`EngineBridge.ts`（桥接）、Android 端 JNI。

## ADR-002：一套前端 API，引擎后端可插拔

**决策**：UI 只依赖 `IEngine` 接口，平台差异压进 EngineBridge 一层。

**理由**：皮卡鱼官方 App 就是「一套 Vue 前端 + 两套引擎后端（WASM/原生 .so）」。训练器需要桌面与移动多端，若 UI 直接依赖具体引擎，会产生 N×M 的组合复杂度。

**落地**：
- Web 端：`NativeEngine.web.ts`（当前 mock，未来 WASM）
- App 端：`NativeEnginePlugin.kt` → JNI → `.so`

## ADR-003：规则引擎自研，perft 做回归

**决策**：不用 `python-chess`（只支持国际象棋），自研约 300 行规则，用 perft 计数回归。

**理由**：规则错了，评分、解说、画像全部不可信。perft 是可自动化的硬基准，开局 `perft(1)=44 / perft(2)=1920` 是公认值，一眼能验证正确性。

**落地**：`src/chess/rules.ts` 的 `perft()` 与 `runPerftSelfTest()`。

## ADR-004：info 流节流——只保留最后一帧

**决策**：引擎 info 每秒可推几十上百行，桥接层聚合后只把最新一帧发给 UI。

**理由**：不节流会冲垮主线程，这是接 UCI 引擎最常见的坑。

**落地**：`EngineBridge._dispatch('info')` 用 `lastInfo` 合并帧。

## ADR-005：对手强度用 MultiPV + 温度采样，不靠限深度

**决策**：候选着法按 `p_i ∝ exp(-(cp_i - cp_best)/T)` 抽样，而非直接降 depth。

**理由**：低深度引擎走出的棋"既不合棋理、也没人性特征"；温度采样选的是引擎认为合理的次优着法，弱得像人而非像傻子。

**状态**：已实现于 `src/training/difficulty.ts`——六档预设 + `pickMove()` 温度采样 + 失误注入，内核自检验证入门档候选分散、满血档恒选最优。

## ADR-006：评分口径采用 cp loss 分档

**决策**：本步失分 = 引擎首选分数 − 实际走法分数，按 <20 优秀 / 20-50 良好 / 50-100 不精确 / 100-250 失误 / >250 严重失误 分档。

**理由**：国际象棋社区成熟口径；cp 转胜率的系数需针对象棋校准（不能套用国际象棋的 0.0037）。

**状态**：已实现于 `src/training/grader.ts` + `src/composables/useCoach.ts`——在走前局面用 MultiPV(8) 找最佳分与实际着法分，算差值分档；内核自检验证最佳着法=优秀/0cp、低级失误=严重失误/350cp。
